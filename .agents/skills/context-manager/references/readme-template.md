# README.md Template

## Document Purpose
`README.md` is the front door for **humans** landing on the repository (GitHub's rendered landing page, package registries, search results) — it answers "what is this, and how do I get it running" in under a minute. It is intentionally shallow: depth belongs in the other control docs, and `README.md` should link to them rather than duplicate them.

Do not let `README.md` become a second copy of `ARCHITECTURE.md`, `CONTRIBUTING.md`, or `INTENT.md` — if a section is growing past a few lines, that content belongs in the dedicated doc with a link left behind.

---

## Canonical Structure

```markdown
# [Project Name]

[One-sentence description — same framing as INTENT.md's Problem/Outcome, compressed to a tagline. Do not ship the default scaffold description (e.g. "bootstrapped with create-x-app") once the project has real purpose.]

## Getting Started

Prerequisites: [runtime + version, package manager + version]

```bash
<install command>
<dev server command>
```

Open [http://localhost:PORT](http://localhost:PORT) to view it.

## Usage
[The smallest example that shows the thing working — a command, a code snippet, or a screenshot. If there's nothing to show yet (pre-feature scaffold), say so plainly instead of omitting the section silently.]

## Roadmap
[Optional. A short list of what's next, or a link to `INTENT.md`'s Open Questions / an issue tracker. Omit the heading entirely rather than leaving it empty.]

## Project Status
[Where this project actually is right now — prototype, pre-MVP scaffold, production. Link to `INTENT.md` for scope and open questions rather than restating them.]

## Governance Rules

1. **Shallow by Design**:
   Anything longer than a short paragraph under a `README.md` heading is a sign that content belongs in a dedicated control doc instead. Move it and leave a link.
2. **No Scaffold Boilerplate**:
   Default text generated by `create-*-app`/framework CLIs (generic "Getting Started"/"Learn More"/"Deploy on Vercel" boilerplate with no project-specific content) must be replaced once the project has real identity — a `README.md` that still describes the scaffolding tool instead of the product is a drift signal, not a placeholder to leave alone.
3. **Commands Must Be Copy-Pasteable and Correct**:
   Every command shown must match the actual `package.json` scripts / repo tooling at the time of writing — verify against `package.json` rather than writing generic `npm run dev` if the repo pins a different package manager.
4. **Link, Don't Duplicate, the Other Pillars**:
   Once `INTENT.md`, `ARCHITECTURE.md`, `CONTRIBUTING.md`, etc. exist, `README.md`'s job is to route readers to them, not restate them.
5. **Repository Location**:
   Placed at the repository root as `README.md` — this is also typically the package registry / GitHub-rendered landing page, so it must render correctly as GitHub-flavored Markdown.
6. **Optional Sections, Included Only When They Earn Their Place**:
   The wider README convention (makeareadme.com's "Suggestions for a good README": Name, Description, Badges, Visuals, Installation, Usage, Support, Roadmap, Contributing, Authors/acknowledgment, License, Project status; and the badge-heavy [Best-README-Template](https://github.com/othneildrew/Best-README-Template) pattern: About/Built With, Getting Started, Usage, Roadmap, Contributing, License, Contact, Acknowledgments) also lists Badges, Support/Contact, and Authors/Acknowledgments. Add a badge row or a Contact/Acknowledgments section only if the project is public-facing and it adds real information (CI status, latest version, license badge) — for an internal/private/pre-release repo, skip them rather than cargo-culting shields.
