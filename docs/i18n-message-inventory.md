# i18n Message Inventory

## Scope

Task 1 establishes the app-owned message contract in `src/lib/i18n/`. It supports exactly `en` and `pt-BR`; both catalogs have the same stable-key shape and are type-checked with `AppMessages`.

This task intentionally does not replace literals in application components or shared primitives. A later migration task should consume the catalog and map Firebase error codes before rendering them.

## Firebase UI ownership and exception handling

Firebase-owned authentication labels, prompts, and messages remain in the existing `getTranslation(ui, ...)` infrastructure and are deliberately not duplicated in the app catalog. Current consumers include the sign-in, policies, SMS multi-factor, TOTP multi-factor, and multi-factor assertion components. Examples include `signIn`, `emailAddress`, `password`, `forgotPassword`, `signUp`, `verificationCode`, `sendCode`, and `mfaAssertionPrompt`.

`src/components/sign-in-auth-form.tsx`, `src/components/sms-multi-factor-assertion-form.tsx`, and `src/components/totp-multi-factor-assertion-form.tsx` currently render caught `FirebaseUIError.message` values directly, with `String(error)` as a fallback. Those strings are external Firebase/runtime inputs, not catalog copy. A follow-up must map Firebase error codes to `errors.auth.*` and fall back to `errors.auth.unknown` or `errors.generic.unexpected`; raw exception strings must not be treated as translations.

## New app-owned error coverage

The catalog reserves `errors.generic.*` for application failures and `errors.auth.*` for the future Firebase-code mapping. No current component consumes these keys in Task 1.
